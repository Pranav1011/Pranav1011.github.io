## TL;DR

- **Problem:** a Formula 1 question-answering agent had 79 overlapping tools.
- **What I did:** built an 8-tool set that covers all 79, with a test proving nothing was lost. It is measured and tested, not yet live: the agent still binds the full 92.
- **Result:** tool definitions 85% smaller (13,487 → 2,014 tokens), all 79 capabilities intact. Switching the live agent over is next.

## The problem

The agent answers questions like "Compare Verstappen and Norris's tyre degradation in Singapore 2024" or "What if Max had pitted on lap 33 instead of 38?" It covers seven seasons, 2018 to 2024. To do that it sits on a polyglot store: TimescaleDB for lap and telemetry time series, Neo4j for the knowledge graph of drivers, teams and races, and a Qdrant vector index for retrieval.

{/* src: F1 RIA/README.md Overview ("7 years of data (2018-2024)"), Architecture */}

As features grew, so did the tool list. By the time I measured it, the agent had 79 TimescaleDB tools whose definitions came to 13,487 tokens. That’s a lot of surface for a model to choose from: the model has to pick one function out of 79 near-duplicates like "lap times by driver", "lap times by stint" and "lap times by compound."

## Approach

**Measure first.** Before changing anything, I wrote a measurement script that serializes the agent's tool definitions the way LangChain formats them for a model and counts tokens with tiktoken. That gave a baseline of 13,487 tokens for the TimescaleDB tools alone.

{/* src: backend/eval/measure_consolidation.py; consolidation.json */}

**Consolidate by intent, not by table.** The 79 tools collapsed naturally into a few questions people actually ask: race analysis, driver stats, standings, comparisons and what-if scenarios. I built eight intent-level tools on those lines: five parameterized dispatchers plus three standalone tools. Each dispatcher routes to the original underlying function and filters arguments to that function's signature, so none of the originals had to change. The set is measured and tested but not yet live: the running agent still binds all 92 tools.

{/* src: backend/agent/tools/consolidated_tools.py; test_dispatch_routes_and_filters_args; README "Measured result" (5 dispatchers + 3 standalone) */}

**A guarded escape hatch.** For questions the dispatchers don't cover, the agent falls back to text-to-SQL that is validated as read-only before it runs. The model gets flexibility without write access to the database.

{/* src: backend/agent/validation.py; tests/test_tools/test_sql_validation.py */}

**Grounding.** A query-understanding step parses each question into entities, sub-questions and a HyDE-style hypothetical answer describing what a complete response should contain. The plan is built from that, and answers are built from the race data and telemetry it retrieves. When the data isn’t there, it says so and names what failed instead of guessing; with no database reachable, that notice comes back at once, before any model call.

{/* src: no-data path + preflight: README "No data, no answer", "No data services, no model calls"; ENGINEERING_LOG.md 2026-11-11 "Preflight before any LLM call". HyDE — agent/prompts/understand.py:21, agent/nodes/understand.py:139 (main). NOTE: hypothetical_answer is generated but not yet passed to vector search; see docs/SOURCES.md */}

**The rest of the system.** The agent runs on LangGraph behind FastAPI, with a multi-provider LLM router: OpenAI, Groq, DeepSeek or Gemini when a key is set, falling back to a local Llama 3.1 8B through Ollama, which is the default and needs no key. A Next.js chat front end streams the answer and opens a chart beside it when there is something to plot.

The zero-loss claim is enforced by a test, not asserted: `test_every_timescale_tool_is_covered_exactly_once` fails if any of the 79 original functions becomes unreachable or is covered twice. ## What's next

The consolidated set is built and tested, but the live agent still binds the full 92 tools (79 TimescaleDB, 8 Neo4j, 5 vector search). Switching the binding is next: it touches the execute step and the planner’s tool names, and needs the databases running to validate answers end to end. The consolidation covers the TimescaleDB tools, which were 88% of the original token cost; the 13 Neo4j and vector tools come after. The bigger open question is accuracy: fewer, better-named tools should improve tool selection, and I want to prove that with a labelled question set scored end to end, rather than assume it.
